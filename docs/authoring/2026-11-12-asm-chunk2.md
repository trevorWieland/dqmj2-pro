The 24 rows are 6 ARM (main 2, ov000 2, ov005 1, ov006 1) and 18 Thumb (main 1,
ov006 17). Every shipped row is byte- and relocation-exact, one address-named translation
unit per function, with one mutated-instruction negative control per row. The lane keeps
the round-7 ARM rules and adds `main_thumb`/`ov006_thumb` rules (`p033`, the Thumb form of
`p003`) for the Thumb rows that sit beside the ARM ones in this lane. #189's own lane and
rules are untouched.

## C was attempted first, per row

The Thumb half of the population was swept with three plausible C bodies per row before
the dedupe (89 distinct rows, 267 compilations): **0 matched**. The closest body across the
24 rows shipped here is 1 byte off (`ov006:0x021efd60`); every row resists C, so every row
ships as transcribed assembly. That is expected for this class: the image keeps rotated
loops with the test at the top, block copies predicated on the result, and Thumb `mov`
forms the compiler canonicalises to a different encoding.

## First-try rate

22 of the 24 rows matched on the first compilation with the lane's rule set (**91.7 %**).
Two needed one lexical correction each, both the same spelling: mwccarm assembles
`mov rA, rB` as the ADD-immediate form (`add rA, rB, #0`) while the image holds the
LSL-#0 form, so `mov rA, rB` was written `lsl rA, rB, #0` in
`ov006:0x021efd60` (1 line) and `ov006:0x021fd4ac` (4 lines). No operand, branch or
relocation was edited by hand.

## The row that hides a jump-table word: `main:0x02025578`

Round 7 skipped this row because the pinned objdump leaves a word inside its measured
extent as `<unknown>`. Hand-decoded, it is not one function body:

| extent | bytes | content |
| --- | --- | --- |
| `0x02025578`-`0x0202562c` | 180 | code; ends `ldm sp!, {lr}; bx lr` |
| `0x0202562c`-`0x0202572c` | 256 | **data**: a monotone reciprocal table, bytes `0xff,0xff,0xfe,0xfd,...,0x80,0x80` |
| `0x0202572c`-`0x02025930` | 516 | code; branches back into the prefix at `0x020255a8` |

The `<unknown>` words are not the problem: they are ordinary ARMv5 register-shifted
data-processing forms (`and r0, r0, r0, lsl r1` = `0xe0000091`, `add r1, r0, r2, lsl r1` =
`0xe0801092`) that the round-7 decoder already handles. The blocker is the 256-byte table.
mwccarm's inline assembler has no data directive: `.word`, `dc32`, `.4byte` and `.byte`
were each probed inside an `asm` block and each is rejected as an unknown mnemonic. A
single `asm` function therefore cannot carry the row's measured bytes.

The decode also shows the boundary is not a function boundary. The only PC-relative
address computation in the extent, `sub r0, pc, #148` at `0x020255b8`, evaluates to
`0x0202552c` — before the row, inside the previous function's code (which
`src/hardware/main/native_main_hw_02025504.s` already reconstructs). No PC-relative load
or literal-pool slot in the extent names the table at `0x0202562c`. The table belongs to
the soft-float division/normalisation family the code implements (the prefix manipulates
`clz`, exponents and mantissas; the table is the usual 256-entry reciprocal lookup), but
the ledger's measured extent merges that table with code from at least one function. It is
left unscheduled rather than shipped as a mis-bounded body.

`main:0x0202654c` (1,348 B) has the identical construct: code to `+0x138`, the same
256-byte `0xff`-`0x80` table at `0x02026684`, then code. Its one address computation
(`sub r0, pc, #36` at `0x020265a0`) likewise does not name the table.

## Method (after the rebase)

1. **Re-run the scan, diff against `src/`.** `ops/scan_chunk_shapes.py` reproduces the
   round-7 numbers exactly (365 rows / 118,042 B; 145-row pool / 75,974 B). The 64-row
   remainder is the clear part not shipped by round 7. `ops/unclaimed.py
   --check-addresses` against a pristine `origin/main` (`f5053288`) `src/` reports **0 of
   the 24 shipped addresses already defined**; the 56 duplicate rows the branch had
   transcribed before the rebase are exactly the ones #189 claims, and were dropped.
2. **C attempt per row.** `ops/probe_c.py` compiles three plausible bodies and diffs the
   whole extent after relocation patching; the closest body is recorded in the row table.
3. **Transcribe from the image** with the lane's rule (`p003` ARM, `p033` Thumb) using the
   shared `ops/transcribe_chunk.py`. Its Thumb spelling layer (two-operand ALU forms,
   implicit writeback, `[rN, #0]`, flag-suffix rules, `R_ARM_THM_XPC22` patching) was
   landed by #189 and is reused here; the `_thumb` sibling directory only tells the
   verifier where to find a mixed-mode lane's Thumb files.
4. **Gate.** `ops/verify_asm_chunk_scan.py` compiles every file through its resolved rule,
   patches relocations the way `whole_image_link` does, compares every byte, checks every
   `R_ARM_ABS32` image word against the object symbol plus addend, and runs one mutated
   instruction negative control per row.

## Source-form rules these rows keep

1. **An `asm` function body is the reconstruction form for a row that resists C.**
2. **A pool word is a relocation, not a constant.**
3. **A call is a named symbol, never a raw offset**; a Thumb code pointer keeps its `+1`.
4. **One negative control per row.**
5. **One address-named file per function**, in the mode-specific directory.

## Unknowns

Byte identity establishes the code, not the meaning. Each file states its own unknowns;
the recurring ones are the record layouts behind the block copies (strides 0x34, 0x36,
0xc4, 0x140 in the ARM rows; the pointer pairs and 8-register blocks in the Thumb rows),
the callee contracts of the `native_fn_` targets, and which producer allocates the
destination blocks the copy loops fill. The reciprocal tables in the two documented
`main` rows are decoded as tables (content, bounds, monotonicity) but their producer and
consumer are not established by the measured bytes.
