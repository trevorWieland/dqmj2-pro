# main rows, batch 3: the Thumb population

Status: authored and verified 2026-11-11. First dedicated pass over `main`'s
**Thumb** rows: 201 unmatched rows (62,128 bytes) that no lane had opened.
Four rows are byte- and relocation-exact, **202 bytes**; the rest of this note is
the measured reason the population behaves differently from the ARM batches, and
the evidence that makes the four rows safe.

## What was attempted

| stage | rows | outcome |
| --- | --- | --- |
| disjoint-address sweep | 201 | 201 unmatched, 0 with a ledger relocation table |
| small-row target list (< 128 B) | 81 | 32 taken as the first batch (1,364 B) |
| automatic m2c draft search (5 option sets x 2 profiles) | 32 | 0 exact, 12 near (2-20 bytes off), 20 undraftable |
| hand-authored from the image | 18 | 4 exact |
| shape-twin search against 1,418 accepted Thumb rows | 32 | **0 exact twins** |

First-try rate is poor and worth stating plainly: **1 of the 4 shipped rows was
exact on its first authored form** (`0x0208ed2c`); `0x0208ba68` needed the
condition m2c lost to an `M2C_ERROR` repaired, `0x020a3d9c` needed the loop-carried
node named, and `0x020a8bc4` took three forms before the countdown do/while was
right. Across the 18 hand-authored candidates the first-form exact rate is 1/18.

## Method

1. **Neighbour first, then the compiler.** The accepted Thumb corpus around the
   targets is dense: 1,418 accepted rows, 778 compiled with `-O4,p`
   (`-ipa file -lang c99 -thumb`) and 506 with the `-O2 -inline off` profile.
   Three accepted neighbours in the 0x0208b000 band were recompiled here against
   the image before any row was written: `0x0208b70c` (`src/main/p1h_main_thumb`),
   `0x0208b8e0` (`linked-interworking-20261029-main`) and `0x0208b7cc`
   (`thumb-runtime01`). All three reproduce exactly under **module main, mode
   thumb, profile p032, mwccarm 2.0/base (`7150fa4f`)**, which is the rule the
   new lane uses. The `-O4,p` profile was also tried on every shipped draft and
   changed nothing for these four rows.
2. **Decode the image, do not guess the relocation table.** Every one of the 201
   unmatched rows has `dependencies: []` in the ledger, so a row's call sites
   and pool words are measured from `extract/arm9/arm9.bin` and then pinned in
   the verifier. The pinned table for each row is the object's table.
3. **Draft with m2c, then repair the form.** `tools/m2c` over the dsd assembly
   (`asm/_dsd_gap@main_3.s`) produced usable drafts for 12 of 32 small rows.
   The recurring repairs: a lost flag dependency (`adds` before `bne` becomes
   `M2C_ERROR`), a pointer increment on a `u16 *` that doubles the stride, and a
   loop-carried value that needs a named local.
4. **Shape clustering with literal pools and branch immediates masked** found no
   donor: no accepted Thumb row shares a masked extent with any of the 32
   targets. Unlike the ARM batches, this population cannot be cloned from its
   accepted neighbours.

## The four rows

One file per function in `src/main/t1_main_thumb/`, compiled under the new
`src/main/t1_main_thumb/**` rule (module main, **mode thumb**, p032, 2.0/base).

| address | bytes | shape | relocs | control diff |
| --- | --- | --- | --- | --- |
| `0208ba68` | 56 | retire the 0x021cfea0 record, publish flag 0x44 | 6 | `[28]` |
| `020a3d9c` | 60 | drain the 0x021d2300 node queue in size class 4 | 3 | `[14, 15]` |
| `0208ed2c` | 44 | acquire the 0x0208ed58 validator, `~0x30` on failure | 4 | `[10]` |
| `020a8bc4` | 42 | stage eight bytes, retag first, hand to 0x02090310 | 2 | `[6]` |

`0x0208ed2c` is also the Thumb function-pointer evidence row: it takes the
address of `0x0208ed58` with a **+1 addend** (`extern u8 native_fn_0208ed58[]`
and `native_fn_0208ed58 + 1`), and the verifier requires the +1 slot to resolve
to a Thumb ledger row.

## Verification

`python ops/verify_main_thumb_1.py` recompiles every row with the resolved
source-unit rule, patches the relocations with the mode-aware
`form_search.relocate` + `TargetModes`, and requires, per row:

* the patched text is byte-identical to the measured extent;
* the object's relocation table equals the pinned table (offset, kind, symbol);
* every `R_ARM_THM_CALL` is a Thumb call in the image, encoded BL for a Thumb
  target and BLX for an ARM target;
* every `R_ARM_ABS32` slot has addend 0 or 1, and a +1 addend resolves to Thumb;
* one whole-C negative control compiles and fails at the pinned offsets.

Result: **4 rows, 202 bytes, 0 failures, 4 controls failed as expected.**
`python public_tools/source_units.py --root . --check` reports `unresolved: 0`
with the new rule. `python ops/check_duplicate.py --root .` over the four
addresses against the pristine tree reports **0 already defined**.

## What this says about the Thumb population

It does **not** behave like the ARM population. The ARM batches got 16/30 whole
donors from shape clustering and a 57% first-try rate from cloned neighbours.
For these Thumb rows: (a) no accepted row is a shape twin, (b) m2c gets the
mechanism right but the allocation/loop form wrong on 12 of 32, (c) the
divergences are small (2-25 bytes) but systematic -- writeback `stm`, pool-load
hoisting, and loop rotation. The remaining 201 rows need a form search that can
express those three idioms, not a bigger donor corpus.

## Unknowns

Every row states its own unknowns in-source. Byte identity establishes the code,
not the gameplay meaning: the ownership of the 0x021cfcf8 / 0x021d2300 /
0x021cfea0 blocks, the callee contracts behind the three helpers, the meaning of
the size class 4 and selector 1, and the staging record's layout all remain open.

## Reproduce

```
python ops/verify_main_thumb_1.py
python ops/verify_main_thumb_1.py --pin        # reprint the pinned table
python public_tools/source_units.py --root . --check
python ops/check_duplicate.py --root . --address 0x208ba68 0x20a3d9c 0x208ed2c 0x20a8bc4
```

The verification needs a private checkout with `manifest.json`, `extract/` and
the pinned toolchain, like the other `ops/` tools.
