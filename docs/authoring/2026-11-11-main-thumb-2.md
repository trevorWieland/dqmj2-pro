# main rows, batch 4: the Thumb form-search dimensions

Status: authored and verified 2026-11-11. Second dedicated pass over the
main-module **Thumb** population left by batch 3. Seven rows are byte- and
relocation-exact, **236 bytes**, all in `src/main/t1_main_thumb/` under the
existing lane rule (module `main`, mode `thumb`, profile p032, mwccarm
2.0/base `7150fa4f`). The batch also lands the instrument the population
needed: `ops/form_search_thumb.py`, which adds the three layout dimensions the
batch-3 note named as the blockers.

## The instrument

`ops/form_search.py` was a literal text grid over one template. The remaining
rows fail for three *layout* reasons that a fixed grid cannot express, so
`ops/form_search_thumb.py` drives a per-row spec file through three named
dimensions:

| dimension | what it varies | why it can move bytes |
| --- | --- | --- |
| `WRITEBACK` | array indices, pointer walk, pointer walk with a live advanced pointer, struct assignment from a local, fill loop | mwcc only fuses a store and its address increment into `stm r0!, {…}` when the advanced pointer stays live, or copies a multi-word struct through `ldm`/`stm` |
| `HOIST` | store/call order, comma and named-temp spellings, and the call-arity hypotheses the row spec supplies | a live third argument keeps r2 occupied, so the literal-pool word lands in r3 *after* the store; a dead argument lets mwcc hoist the load and reuse r2 |
| `LOOP` | `for`, `while`, countdown `do`/`while` and `goto` spellings | the rotated countdown has no pre-test branch; the pre-tested forms do |

A spec names the address, size and module, points at a template, and lists the
alternatives per dimension (or asks one of the libraries to generate them):

```json
{
  "address": "0x020B5890", "bytes": 12, "module": "main",
  "template": "020b5890.c",
  "dimensions": {
    "HOIST": ["    native_fn_020b4108(a, p);",
              "    native_fn_020b4108(a, p, c);"]
  }
}
```

A missing dimension is one empty alternative, which is the control: the
expanded source is byte-identical to the template with nothing substituted.
`python ops/test_form_search_thumb.py` proves each dimension produces at least
one observable machine-code difference, and proves the controls do **not**
change the object: (a) no dimension leaves the source and object identical,
(b) two equivalent spellings of the same return compile to the same bytes.
Eleven tests, all passing against the lane toolchain.

### Mechanistic finding

The pool-load difference is **argument liveness**, not statement order:
`f(a, p)` compiles to `ldr r3, pool; movs r2, #0x67; strb r2, [r1, #2]; bx r3`,
while `f(a, p, c)` — where `c` keeps r2 live — compiles to
`movs r3, #0x67; strb r3, [r1, #2]; ldr r3, pool; bx r3`. mwcc enforces the
prototype, so the arity hypothesis must change the whole row source (the spec
templates do); a two-argument call against a three-argument prototype is a
compile error, not a variant. Four rows were resolved by exactly this change,
which is this batch's highest-yield result.

## Ranking and bounded search

`python ops/form_search_thumb.py --rank` ranks the 197 rows by
`(bytes, -idiom_count, address)`: smallest first, then rows whose dsd
disassembly shows a writeback `stm`, a pool load or a backward branch.
Measured on the starting population:

| bucket | rows | bytes |
| --- | --- | --- |
| 2–63 B | 28 | 2,156 |
| 64–127 B | 49 | 7,624 |
| 128+ B | 120 | 52,146 |
| total | 197 | 61,926 |

Idiom coverage in that population: pool load 160, loop 102, writeback `stm` 7
(rows can carry several). Every spec search ran under the 300 s per-row budget
with 1–6 candidates; no row came near the budget, so no search was truncated.
The budget is enforced by `--time-budget` and reported when it fires.

## Dimensions: what produced differences, and the per-idiom rate

| dimension | rows attempted | exact | hit rate | note |
| --- | --- | --- | --- | --- |
| `HOIST` | 4 | 4 | **100%** | all four are the live-third-argument pool-load case |
| `WRITEBACK` | 3 | 0 | 0% | the unit tests prove `stm` is reachable (`p[0]=v; p++; return p;` and a 3-word struct copy), but the three real rows still differ in allocation: `02000E04`/`02008F3C` want three zero registers and grouped `stmia`; `02000DE8` wants the zero in r3 and `-arg1` in r2, and every statement order tried keeps the zero in r2 |
| `LOOP` | 1 | 0 | 0% | `020A8B8C` is a countdown `do`/`while` with a live argument; the best form is 52 B against 54 B, because mwcc tail-merges the early `return 0` and omits the image's second `add r1, sp` |
| none of the three (plain C) | 5 | 3 | 60% | `020A5FE4` (52 vs 54 B) and `020A8DC0` (84 vs 88 B) are register/layout near-misses |

Distinct rows attempted: **13**; exact: **7**. The writeback and loop rows are
recorded as measured negative results, not as silent failures. `02092BA0` is
included as evidence that the plain-C path still works.

## Permuter gate

The batch rule is "run the permuter for rows that are exact-size and
textDiff<=3". **No attempted row met both conditions.** The closest rows were
`020A8B8C` (52 vs 54 B), `020A5FE4` (52 vs 54 B), `020A8DC0` (84 vs 88 B) and
`0208DD90` (64 vs 68 B); `02000DE8` is exact-size but 16 bytes away. The
permuter was therefore not started, and the gate is reported with zero
qualifying rows rather than a misleading run.

## Unknowns

Every row states its own unknowns in-source. Byte identity establishes the code,
not the gameplay meaning: the record layout behind `020B5890`/`020973C8`, the
contract of the ARM helper behind `02092C98`/`02092CA8`, the ownership of the
0x021D1B88 / 0x021CFD48 / 0x021D2374 blocks, the 64-bit tick returned by
0x02007A9C, and the meaning of the 0x0A event and 0x12 probe answer.
