`python ops/verify_ov000_pass3.py` recompiles every row with its resolved
source-unit rule, patches `R_ARM_PC24` with the same formula
`public_tools/repo_build.py` uses and the rest with `ops/form_search.py`, compares
the whole measured extent at the ledger row's `binaryOffset`, checks that each

## Method

The lane is neighbour-first. Before authoring a row, two or three accepted
neighbours in the same address region were read from `ledger/functions.jsonl`
(`functionMatched` + `sourceUnit`) and their idiom was mirrored: a global block
is `extern u8 native_data_<addr>[]` reached through `M2C_FIELD`, never
`*(u8 *)(base + off)`; a named block/row pointer is used where the image
materialises the row base with `mla`; declaration order is the register-rotation
knob and was swept when the first form missed.

Candidate screening is source-tree first. An address is skipped when it
already appears in any `src/` file name or when the ledger row it names is
matched. The ledger alone is not enough: it is stale for both pass-1 lanes,
and nine rows that first looked unmatched here turned out to be already
defined -- eight in `src/ov000/pass1_20261111` and `0x021d8528` in the
2026-10-29 leaf packet -- and were deleted before commit. That is why the
shipped lane is thirteen rows, not the twenty-two drafted.

## What made the rows match

1. **Family templates scale.** The eight 48/52-byte table scans at
   `0x021df578`/`0x021df624`/`0x021df6d0`/`0x021df77c` and
   `0x021df544`/`0x021df5f0`/`0x021df69c`/`0x021df748` are two source forms with
   constants substituted: a `do`-while over a stride-0x18/0x30 table that either
   returns the first empty slot (-1 when full) or tests `id == *slot` and returns
   1/0. Counter before pointer is the allocation order the image uses; the
   compare direction (`id == *slot`, not `*slot == id`) is a two-byte diff.
2. **A row pointer beats one combined offset.** `0x02223d40`/`0x02223cc4`/
   `0x02229f38` only match through `u32 *row = (u32 *)(block + index * 0xc);
   row[field]`; the equivalent `M2C_FIELD(block, u32 *, index * 0xc + field * 4)`
   compiles four bytes longer because mwcc folds the two multiplies differently.
3. **`switch` is sometimes the only source shape.** `0x0220a284` and
   `0x022109b8` need `switch` with shared cases: the `||` form becomes a range
   check and loses the image's `cmpne` chain.
4. **Signedness is a code shape.** `0x02209bc0` shifts the value arithmetically,
   so the split value is `s32` and each stored byte is masked afterwards.
5. **Per-row compiler stays `p001` + 2.0/base.** Every row was accepted under the
   same rule as the pass-1/pass-2 lanes, so no compiler-selection exception is
   introduced.

## Near-wins

Of the twelve documented pass-2 near-wins:

* **1 landed**: `0x02215cb4` (48 B). The image loads the bitmap word into r0 and
   keeps the mask in r2. The parked form loaded the word first, which puts the word
   in r2 and the mask in r1 (7-byte diff). The accepted form copies the mask into a
   named value *before* the load, keeps the shifted mask in a second named temp,
   and indexes the word inside the `if`; decomp-permuter found it after 103 s.
* **2 were already exact in pass 2**: `0x021e60a8` and `0x021e61c0` re-verify
   byte-exact from `src/ov000/pass2_20261111` (the shipped sources avoid mwcc
   sinking the zero into `moveq` by keeping the result and table named and the
   record computed before the test). They are not duplicated in this lane.
* **9 remain open.** `0x022096bc`/`0x0222189c` still allocate the handle to r0
   instead of r1; `0x022273d4` keeps the row base in r2 instead of r3;
   `0x021e8c50`/`0x021e8de8` still use r1/r2 instead of lr/ip; and the four
   80-byte rows (`0x021efd38`, `0x021efdcc`, `0x02217a78`, `0x02217b8c`) still
   compile to 76 bytes because mwcc fuses the two stack-argument stores into one
   `stm`.

### The stm-fusion rows were not cracked

Nothing shipped for those four. What was tried and measured, all still 76 B with
one `stm sp, {r1, ip}`: the declared pair array, a struct pair, two named `u16`
locals, `volatile` pair/struct writes, separately named `4`/`1` temps, a struct
of the three tail arguments passed by value (96 B, worse), variadic and
no-prototype callee declarations, and `u8`/`u16` tail parameter types. A compiler
sweep over all 24 installed mwccarm builds shows only 1.2/sp3 and 1.2/sp4 emit
two separate `str` (80 B, 8 bytes off, and with `stmdb`/`ldm` prologue forms that
do not match the image); every 2.0/dsi build fuses. The rows therefore need a
source-level fusion barrier that was not found, or a compiler decision with a
per-row rule -- not a silent profile change.

## Tooling fix required by this lane

ARM rows with a call could not be permuted before this pass:

* `ops/mwcc_objdump.py` had no name for relocation type 1 (`R_ARM_PC24`), which
   is the spelling 2.0/base emits for an ARM `bl`; it now renders type 1 with the
   same `R_ARM_CALL` name as type 28 so the permuter can parse ARM workspaces.
* `ops/permuter.py` zeroed *every* relocation slot in `target.o`. A branch slot is
   the instruction word, so a zeroed `bl` became `andeq` in the target while every
   candidate rendered `bl <symbol>`; base score was ~210 and score 0 unreachable.
   Data slots are still zeroed, branch slots keep the base object's unresolved
   instruction, and `row.json` records `branchSlots`. The project's own byte gate
   still measures the real image at the slot.

## Unknowns

Every file states its own unknowns in-source. In summary: the stride-0x18/0x30
tables and their ids; the 0x2cc record's 0x274 state byte; the 0x2c4 record's
0x2c1 flag; the 3-byte and 6-byte row layouts; what the 0x022463dc/0x02246424
parallel tables index; the meaning of the 0x16/0x4d/0x4e constants; and the
services reached through the forwarded arguments. Byte identity establishes the
code, not the gameplay semantics.
