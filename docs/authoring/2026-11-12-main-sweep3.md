Status: adopted 2026-11-12. `ops/gen_main_sweep3.py` is the generator,

## The remainder is a singleton tail, not an unexploited family

The cluster question was asked first, because coarse-skeleton generation is the
cheapest yield there is. Over the 490 unclaimed rows of 192 bytes or less, the
skeleton (mnemonic plus operand kinds, every register and immediate free) gives
**471 clusters of which 456 are singletons**. Only eight multi-row clusters land
inside this lane's size window, and they are small: one of four rows, two of
three, five of two. The big families were already taken by the earlier main
lanes, and every remaining row is largely its own shape. That is why this lane is
transcription-led rather than generation-led.

| cluster | rows | bytes | relation |
| --- | ---: | ---: | --- |
| `0x020481b8` | 4 | 336 | same body and same relative branch displacements; the four rows differ only in the trailing pool word (`0x021d4bb8`, `…bb2`, `…bb6`, `…bb4`) |
| `0x0200616c` | 3 | 120 | same variadic-forwarder body; `0x02019dd4` differs only in its callee, `0x020061ac` forwards the fifth argument (`sp + 0x10`) to a callee of its own |
| `0x02038174` | 3 | 96 | same guarded-field-call body; the first row keeps the guard in `r2`, the other two in `r3`, and each calls its own `0x0209xxx` helper |
| `0x02067dd4` | 2 | 128 | same sum-over-index body, different count getter, element getter and constant |
| `0x020c22c4` | 2 | 88 | same two-stack-word relay; the sibling relays into the neighbouring row `0x020c22c4` and calls `0x02049e0c` with 0 |
| `0x02045dc4` | 2 | 80 | same three-word argument block, third word 0 vs 1 |
| `0x0202ac08` | 2 | 136 | same pooled one-byte gate and null fallback, different callee pair |
| `0x0205f0f8` | 2 | 136 | same 8-byte-record scan (bit 0 at +7, sign at +4), different table base and record count (16 vs 4) |

Twenty rows fall in those eight clusters: eight representatives were read by hand
and the other twelve generated from the representative's shape with each row's
operands, callees and pool word taken from the image. The remaining **82 rows are
singletons**, transcribed on their own terms. The `0x020481b8` cluster is the
cleanest case of the technique: four rows whose *only* difference is a pool word,
so reading one row settles all four.

## C was attempted first, per row, and lost

Six of the most C-looking rows were written as plausible C bodies before being
transcribed and compiled with the `src/main` rule (`p001`, mwccarm `2.0/base`)
through `ops/probe_c.py`:

| row | bytes | C body | result |
| --- | ---: | --- | --- |
| `0x02087e44` | 20 | indirect call through `*(u32 *)(*(u32 *)(a + 0x14) + 4)` | 20 B, **4 bytes differ**: C loads into `r0`/`r0` and calls `blx r0`; the image loads into `r2`/`r2` and calls `blx r2` |
| `0x02007360` | 32 | save/restore `0x04000208`, poll `VCOUNT` | **52 B** against 32; mwcc materialises the MMIO base through the pool and keeps the loop test at the bottom |
| `0x02008bf8` | 28 | halfword copy loop over a byte offset | **32 B** against 28; C branches around the body instead of predicating `ldrhlt`/`strhlt` |
| `0x0205c25c` | 28 | `return object[6] & (1u << index)` | 28 B, **17 bytes differ**: frame `{r4, lr}` with a different argument/register order |
| `0x02038174` | 32 | null-guarded field call | **28 B** against 32: C keeps the pointer in `r0`, the image reloads `[r0]` after the guard |
| `0x02000de8` | 28 | nine field stores in address order | 28 B, **16 bytes differ**: the store grouping and duplicate-constant handling differ |

**0 of 6 matched.** Every one of them is a source-form-independent codegen
choice (register role, predicate vs branch, reload-after-guard, MMIO base
materialisation, store grouping), which is the same class the round-12 lanes
documented. All 102 rows therefore ship as transcribed assembly.

## The disassembler is Capstone here, and that is a tooling substitution

`ops/transcribe_chunk.py` reads text from `ops/disasm.py`, which shells out to the
pinned LLVM objdump under `tools/android-ndk/r30`. **That toolchain is not
installed in this checkout** (there is no `tools/android-ndk`, and no
`llvm-objdump` on the machine), so `ops/capstone_disasm.py` renders the same text
from Capstone 5.0.7: `--no-show-raw-insn` layout, branch targets printed bare,
register aliases normalised to `r9`-`r12`, and `ldm`/`stm` given the `ia` suffix
the transcriber's spelling table keys on. `ops/gen_main_sweep3.py` installs that
renderer over `disasm.disassemble` and then calls the transcriber unchanged, so
the lane inherits the round-8 dialect rules rather than re-deriving them.

The substitution is validated against two rows the round-7/11 lanes had already
transcribed with the LLVM toolchain: `main:0x02008c14` and `main:0x02007850`
regenerate **instruction-for-instruction identical bodies** (only the header prose
and local-label prefix differ). Anyone who restores the NDK can regenerate this
lane with the same generator and get the same bytes.

## Documented, not shipped

| row | bytes | reason |
| --- | ---: | --- |
| `main:0x0201919c` | 56 | its `blx` is an **ARM BLX-immediate to a Thumb callee**, so the measured word keeps `H = 1` (`0xfbff9d23`). mwccarm assembles `blx native_fn_0200064a` with `H = 0` (`0xfa…`), and the shared patcher (`form_search.relocate`, `R_ARM_PC24`) preserves the compiled top byte, so the image's `H` bit cannot be reproduced. Fixing it needs the patcher to set bit 24 from the target for `0xFA`-class words; that is a shared-tool change, so the row is left out here and recorded rather than forced. |

## Verification and gates

```
python ops/gen_main_sweep3.py --plan ops/main_sweep3_plan.json
python ops/verify_asm_chunk_scan.py \
    --lane src/verified_assembly/20261112_main_sweep3 \
    --fixture ops/main_sweep3_expectations.json
python public_tools/source_units.py --root . --check     # unresolved: 0
```

The verifier compiles each row with the rule its path resolves to, patches every
relocation, compares the whole measured extent, and runs one whole-source
negative control per row. Measured on the shipped lane:

| measure | value |
| --- | ---: |
| rows | 102 (81 ARM in `main/`, 21 Thumb in `main_thumb/`) |
| bytes | 5,080 |
| pinned relocations | 106 |
| pinned pool words | 6 (checked against the image word, never a name) |
| negative controls that differ | 102 / 102 (first differing byte: 0 in 81 rows, 1 in 15, 2 in 5, 9 in 1) |
| verification failures | 0 |
| first-compilation matches | 102 of 103 attempted (99.0 %); the miss is `0x0201919c` above |

Source-first screening: the population was taken from
`ops/unclaimed.py --module main`, which reported 895 unclaimed rows / 282,156 B
before the lane. After the lane the same command reports 793 rows / 277,076 B
with **102 claimed by source**, so every shipped file claims exactly one row and
no row was double-claimed.
