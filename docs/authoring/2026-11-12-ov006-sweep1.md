# ov006 sweep 1: fourteen coarse skeletons, 118 rows, 26,864 bytes

`ov006` was the largest untouched module after round 8: 443 genuinely unclaimed
rows (108,614 bytes; 320 Thumb, 123 ARM). This pass works it top-down by the
project's proven techniques. Fourteen coarse-skeleton families were found and
read; the six-row `A6` family is shipped as **generated C** (one template, six
instantiations), and 112 rows are shipped as **transcribed** `mwccarm` assembly
after three plausible C bodies per row were compiled and all failed. Every row is
byte- and relocation-exact against `extract/arm9_overlays/ov006.bin`
(base `0x021d7240`) with one mutated-source negative control per row.

| form | rows | bytes |
| --- | --- | --- |
| C generated from a coarse-skeleton template | 6 | 672 |
| transcribed from the measured instruction stream | 112 | 26,192 |
| **total** | **118** | **26,864** |

The lane is `src/ov006/g1_ov006_sweep1/{thumb,arm}/ov006/**`, one address-named
`.c` translation unit per function: 62 Thumb rows (10,244 bytes) and 56 ARM rows
(16,620 bytes). Both lanes resolve through two new rules in
`config/source_units.json` (`p033` for the Thumb directory, `p003` for the ARM
directory, both mwccarm 2.0/sp1p5 `89b2fc16`).

## The population and the partition

`ops/unclaimed.py --module ov006` against the round-8 `origin/main` (`f5053288`)
calls 443 of the 500 unmatched ledger rows genuinely unclaimed; the other 57 are
already defined in `src/verified_assembly/20261112_asm_chunk_scan/**`,
`..._asm_chunk_thumb/**` or the `src/ov006/p*` lanes and were dropped before any
drafting. The partition is stated rather than assumed:

* the **17 rows in the copy-triage pool** (`pred>0`, `wb>=2`, or a word run) are
  left to the chunk lane and are not touched here;
* the remaining **426 rows** are this lane's address set;
* of those, 39 rows fall into 14 coarse-skeleton families and 387 are singletons.

A second source-first screen was run on the final 118 shipped addresses against
the pristine tree: **0 already defined under `src/`**. Mentions (callers,
prototypes, comments) do not block a row.

## The skeletons

Exact masked-word matching finds almost nothing in `ov006`: 418 clusters for 443
rows and the largest is six. The coarse key — **opcode + registers + transfer
width fixed, every immediate free, the trailing literal pool stripped** — finds
fourteen real families of two or more rows (39 rows, 4,048 bytes). The
representatives were read from the measured stream; the rest were instantiated
from the family's decoded parameters.

`A6` is the template family: six 112-byte Thumb functions whose instruction
skeletons are identical and whose only differences are three descriptor pointers
in the literal pool. The representative's C body matched byte- and
relocation-exactly on the **first compile** (112/112 bytes, 3 relocations); the
other five were generated by substituting each row's own pool words.

`B4` and `C4` are the same shape as `A6` but with a flags decode between the call
and the control-field writes; their representatives were probed as C (two bodies
for `B4`) and did not reproduce the stack slots and register rotation, so the
family is transcribed. `D4` is parked because two of its rows carry the same
non-address pool constant `0x11d` in two slots, which the assembler would fold
into one; `H2d` is parked because its switch table is data inside the measured
extent.

The 14-shaped `wb=1` classification is a scanner artefact worth recording: the
copy scanner decodes the whole measured extent, so a literal-pool word can look
like a one-block transfer. Measured on the **code extent only**, 437 of the 443
rows carry no copy shape at all and only 6 carry a genuine block move. The
partition above excludes the 17 triage-pool rows, which is the chunk lane's
class, and keeps the false-positive rows as ordinary C/asm rows.

## C was attempted first, per row

The `A6` representative was one body: `fn(ptr, arg)` three times, then five
`(x & ~3) | 3` halfword updates on `0x04001008`/`0x04000008`. It matched first
try. `B4`'s representative was tried as two bodies (direct field expression, and
a volatile-local variant that forces the measured stack slot); both failed, the
closest differing in 50 of 68 bytes, so the `B4` family is transcribed.

Every transcribed row was then compiled as C before it was transcribed, with the
same three plausible bodies rounds 7 and 8 used: a field read, a word copy loop,
and a block-struct copy. **112 rows x 3 = 336 compilations, 0 exact**; the
closest body is 68 bytes off, the median 174.5 and the mean 231.1 bytes off. The
per-row result is pinned in `ops/ov006_sweep1_cattempts.json` (body, object
length, relocation count, differing byte count). No row was shipped as assembly
without that C attempt.

## What the gates had to learn about this population

Each rule was found by a compile error or a byte diff and then held for every
row; no instruction was edited after a row's first transcription.

* **The transcriber's outside-slot refusal was tripped by pool data decoded as
  code.** `thumb_literal_slots` scans the whole measured extent, so a literal-pool
  word such as `0x4800...` decodes as `ldr rX, [pc, #n]` and points outside the
  row. The tool now computes the code end from the first inside slot, drops slots
  decoded at or after it, and only refuses a **code** load that points outside.
  This recovered 28 rows (383 transcribable instead of 355).
* **A conditional flag-setting `MOV` with a shift needs mwcc's condition-first
  spelling.** LLVM prints `lsleq r0, r0, #16` for `MOVeq` with `LSL #16` and the
  S bit clear; `lsleq` and `movseq` are rejected, `moveq r0, r0, lsl #16` is
  accepted, and the flag-setting form is `moveqs`. One row needed the rewrite.
* **An inline pc-relative table is a refusal, not a transcription.** 69 of the
  443 rows write `pc` (`addls pc, pc, rN, lsl #2`, or Thumb
  `add rX, pc; ...; add pc, rX`). The table words are data inside the measured
  extent, so an instruction transcription would encode them as instructions and
  could not match. These rows are screened out of the plan.
* **A duplicated non-address literal is a refusal.** 60 rows load the same magic
  constant from two pool slots; mwcc deduplicates one expression into a single
  slot and the row would be four bytes short. Distinct address-like duplicates
  are nameable (`native_data2_`), duplicated constants are not guessed.
* **The verifier's negative control needed a C path.** `control_source` mutates
  the first numbered register, which exists in an `asm` body but not in the
  generated C rows. The fallback mutates a source constant; the compiled control
  still has to differ from the image, so the generated rows are not vacuous.

## Source-form rules these rows keep

1. **A generated row is C, not assembly.** `A6` is a real C template; its six
   files differ only in the descriptor pointers decoded from each row's pool.
2. **A transcribed row is the measured stream.** The body is the image's
   instruction stream in mwccarm syntax; the literal pool and every branch target
   are read from the image, never guessed.
3. **A pool word is a relocation, not a constant.** A word that is an address is
   a `native_fn_`/`native_data_` symbol; a magic constant stays the numeric
   literal; a duplicated address gets a distinct symbol.
4. **A call is a named symbol, never a raw offset.**
5. **One negative control per row.** The first mutable instruction (or source
   constant, for generated C) is changed and the control must differ from the
   image.
6. **One address-named file per function.**

## Unknowns

Byte identity establishes the code, not the meaning. Each file states its own
unknowns; the recurring ones are the block and field roles behind the
`native_fn_`/`native_data_` targets, the record layouts and strides the
transcribed bodies touch (`0x10`, `0x30`, `0x34`, `0xc`), the helper contracts,
and which producer allocates the blocks the descriptor calls fill. The display
control fields in the `A6` family are known only as five 2-bit halfword fields on
the sub and main engines; their consumers are not established. The six parked
family rows (`D4`, `H2d`) are left open rather than guessed.
