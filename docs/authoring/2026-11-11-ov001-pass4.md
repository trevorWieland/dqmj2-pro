## What made the rows match

1. **The pass-3 publish template is a call-count family, not one shape.**
   `0x0222afc8` (four calls) generalises by inserting literal calls around
   the same 12-byte block copy, command submit and flush: the 104-byte rows
   add one value call, the 120-byte rows add two, the 132-byte rows add the
   `+8` record lookup whose byte `0x1f` feeds the value call, and the
   152-byte rows add the `0x022470c` pair before the flush. The register
   dance (`r4` entry, `r5` other, `r6` record) is identical across all four
   sizes, so one body covers each family after symbol substitution.

2. **The scan family only needed a flag argument.** The `+0x440`
   three-record scan of passes 1-3 appears eight more times at 88 bytes;
   the second service call takes an immediate flag (`0x80000`, `0x80`,
   `0x8`, `0x4`, `0x1`, ...) loaded once before the loop. Everything else --
   the `i == 2` exit before the advance, the `i < 3` loop test and the shared
   `return 0` -- is the accepted `0x0221b748` body.

3. **Rotated immediates must be decoded, not read as a byte.** Two 132-byte
   rows pass `0x04000000` to the closing call; the ARM encoding keeps that
   constant as `imm8 = 1, rotate = 3`, so a generator that copies the low
   byte emits `1` and differs by two bytes. Decoding `ROR(imm8, rotate*2)`
   before writing the C fixed them without touching the template.

4. **Shape clustering is only a screen; the skeleton is the donor.** The
   710 genuinely unclaimed rows contain just three exact masked-shape pairs,
   and no unclaimed row matches one of the 101 accepted rows exactly. The
   productive key is the coarse skeleton -- opcode, register and transfer
   width fixed, every immediate free -- which grouped the 23 x 132 B,
   12 x 152 B, 7 x 104 B and 5 x 120 B publish rows and the 8 x 88 B scans.
   All 23 of the 132-byte rows compile, including the fourteen added in
   pass 5, which matched on their first compile.
