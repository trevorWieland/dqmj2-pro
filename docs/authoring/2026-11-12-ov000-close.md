## The `dcd` carrier for 103 table rows

103 of the 601 dispatch by writing `pc` through an inline table. They ship as
`ops/transcribe_data_rows.arm_c` emits them — one `asm` unit whose data run is `dcd`
lines, the measured `ldr rX, [pc, #imm]` loads left alone, every instruction, branch
target, pool word and table entry read from the image. The carrier is a *body shape*,
not a separate build path: those rows sit in the same ARM directory as the other 498,
so the lane is still one address-named file per function and still one rule fragment.

**Two of the 103 needed a measured extension to the table bounder.** The shared
bounder (`ops/transcribe_data_rows.dispatch_sites`) accepts an ARM table only while
every entry is a `b` word whose target is inside the row. A switch arm that returns
early stores a `pop {.., pc}` word instead, so those tables bounded to zero entries:

* `0x0221c0c4` (1,004 B) — `cmp r2, #11; addls pc, pc, r2, lsl #2`, then twelve
  entries at `0x0221c0e4` whose first is `pop {r3, r4, r5, pc}`;
* `0x02224e38` (172 B) — `cmp r2, #11; addls pc, pc, r2, lsl #2`, then twelve entries
  at `0x02224e60`, again starting with a `pop`.

The extension is contained in `ops/gen_ov000_close.py` (`_arm_table_fallback`) and is
measured, not guessed: an entry counts when the word is a branch into the row *or* an
instruction that writes `pc` as a return (`pop`/`ldm`/`bx`/`mov pc, ..`), and the run
ends at the first word that is neither. Both rows then bounded to exactly the twelve
entries the `cmp #11` dispatch implies, and both verify byte-exact (53 and 3
relocations). The shared tool was not modified, so no other lane's fixtures move.

`0x0221c0dc` is the `addls` site and `0x02224e5c` / `0x0221c0e0` are the fallthrough
`pop` words that live *between* the dispatch and the table — code, not data — which is
why the table starts at `site + 8` and not at `site + 4`.

## The two screen corrections, re-checked on this population

Round 12 recorded both artefacts and this lane re-measured them rather than
inheriting the verdict:

1. **`add rD, pc, #imm` is not a `pc` write.** It is the ADR form of an address
   computation and fully transcribable. The class screen tests the *destination*
   operand, so the ADR form does not defer a row.
2. **A pool word must not be decoded as code when deciding the class.** The screen
   stops at the row's first in-row literal slot; reading the whole measured extent
   would let a literal that reads as a branch condemn its own row.

Both are in `ops/gen_ov000_close.py` (`has_pc_write`, `_code_end`). With both applied,
exactly 103 rows write `pc` and every one of them has a provable table; **0 rows
deferred, 0 rows refused**.

## Source-form rules these rows keep

1. **The body is the measured stream.** Instructions, the literal pool and every
   branch target are read from the image, never guessed.
2. **A data run is emitted as data.** The 103 dispatching rows use the `dcd` carrier;
   their entries are measured words.
3. **A pool word is a relocation, not a constant.** A word that names something in the
   image is a `native_fn_`/`native_data_` symbol; a magic constant stays numeric.
4. **A duplicated value is counted per pool slot, not per load**, and a genuine
   duplicate gets a distinct alias.
5. **A call is a named symbol, never a raw offset.**
6. **One negative control per row.**
7. **One address-named file per function.**
8. **Lane rules live in `config/rules.d/`, never in the shared array.**

## Unknowns

Every file states its own. The recurring ones are the field, block and callee
semantics behind the `native_fn_`/`native_data_` targets, the record layouts and
strides the bodies touch, and which producer allocates the blocks the callee chains
fill. The 103 carrier rows add one: their table entries are transcribed
reachability, not recovered C control flow — the dispatch range and the table bounds
are measured, their meaning is not.
