## The population: 108 plain rows plus 27 the ledger enumerated since

The population is the live screen, not the sweep-2 note: **135 rows, 22,456 B** in
`0x021d7240..0x02204f6c`. Where each row came from is measured against the sweep-1
443-row population cache (`analysis.json`, the only record of that population):

| where the row sits | rows | bytes |
| --- | --- | --- |
| in the sweep-1 population cache, transcribable, never shipped | 108 | 16,836 |
| not in that cache at all (the ledger has enumerated them since) | 27 | 5,620 |

None of the 135 is in a coarse family and none was shipped by sweep 1 or sweep 2, so
the two sets are disjoint and the split is complete. All 108 cached rows are Thumb;
the 27 are 11 ARM and 16 Thumb, and the one row that writes `pc` through an in-row
table (`0x021d7240`) is one of them.

**Why the 108 were left is a screen artefact, not a shape.** The cache's copy score
sets `wb` from any writeback memory instruction, and every function that saves
registers opens with `push {..., lr}` / closes with `pop {..., pc}`. Measured on the
108: `pred == 0`, `runs == 0` and `wb == 1` for **all 108**, and the only writeback
instruction in each row is the prologue/epilogue push or pop — **zero** rows carry a
real `ldm`/`stm` block move. Sweep 2's population predicate required `wb == 0`, so
these rows fell outside it; sweep 1 kept only the 85 largest rows with `wb < 2`. The
sweep-2 note's "110 plain shaped rows" is this bucket, and the live set is two rows
different because the bucket size was an estimate, not an address list.

The 27 rows the cache does not have are the ledger's own growth: the carrier round
(#194) and the aggregate-copy round (#188) both enumerated rows. Their measurement
is the same — the ledger row's `bytes`, `binaryOffset` and `mode` against the image —
so they are drafted on the same terms as the other 108.

The partition of the 135 is measured per row rather than inherited:

* **1 row writes `pc` through an in-row table** (`0x021d7240`, the overlay's first
  row: `subs r1, r0, #28; addpl pc, pc, r1, lsl #2` with seven branch words at
  `+0xf0`). It is the `dcd` carrier's shape and ships through it.
* **134 rows are one instruction run with the literal pool at the end.** All 134
  are expressible by `ops/transcribe_chunk.py` with `constant_aliases` and
  `unique_pool_slots` on; **0 refusals**.

Two corrections to the earlier screens were needed and both are visible in the
count, so they are stated rather than folded in silently:

1. **`add rD, pc, #imm` is not a `pc` write.** The sweep-2 screen returned true for
   any `add` whose operands mention `pc`, which swept up the ADR form of an address
   computation. Four rows (`0x021d85d4`, `0x021db410`, `0x021dbaa4`, `0x021df310`)
   were deferred by that clause and are ordinary transcribable rows.
2. **A pool word must not be decoded as code when deciding the class.** The screen
   also read the whole measured extent, so a literal-pool word decoded as
   `eoreq pc, r0, #244, #4` and condemned those same four rows. The screen now stops
   at the row's first in-row literal slot. With both fixes exactly one row of the
   135 writes `pc`.

the 135 shipped addresses reports **0 already defined**, with 118 rows carrying only
a mention (a caller or a leftover declaration) and 17 clear.

## C was attempted first, per row: 810 compilations, 0 exact

Every row was compiled as C before it was transcribed, through the row's own rule
(p033 Thumb / p003 ARM) and compared with the whole measured extent after
relocation patching. Six bodies per row, not three, because this round named the
form rules that decide whether a C body can match at all:

| body | the form rule it pins |
| --- | --- |
| `field-read` | plain measured field read (the sweep-1/2 body) |
| `copy-loop` | word copy loop (the sweep-1/2 body) |
| `block-struct` | block-struct copy (the sweep-1/2 body) |
| `m2c-field` | `extern u8` array indexed through `M2C_FIELD` |
| `rematerialise` | `u16 *const` re-read after a call |
| `bitfield-flag` | `unsigned :1` on a control word |

**135 x 6 = 810 compilations, 0 exact.** The closest body is 28 bytes off
(`0x021fdde0`), and the closest body by class is `m2c-field` on 126 of 135 rows —
which is what a population of this shape predicts: every row is dominated by
measured call sequences and stack slots, and no fixed body can reproduce a call
sequence. The per-row result (body, object length, relocation count, differing
offset list) is pinned in `ops/ov006_sweep3_cattempts.json`.

The six bodies are a *screen*, not the whole C effort: `volatile` for cross-block
order, named temporaries for operand order and declaration-order sweeps are the
per-row moves that turn a nearly matching body into an exact one, and they are only
worth spending on a body that is already close. With the closest body 28 bytes off
and every row's body a distinct call sequence, the C form of these rows is not
recoverable from the extent in this round; each ships as the measured stream.

## A missing pinned tool, and what replaces it

This replay has `extract/`, `ledger/`, `tools/mwccarm` and `manifest.json`, but not
`tools/android-ndk`, which is where `ops/disasm.py` finds the pinned
`llvm-objcopy`/`llvm-objdump`. Without a decoder no lane can be regenerated at all,
and regeneration is what the source-form rules require.

`ops/disasm_capstone.py` is the documented fallback: same signature, capstone as the
decoder, rendering the text the transcriber expects (branch targets unmarked, the
pin's immediate spellings, `r9`-`r12` spelled `rN`, `<unknown>` past undecodable
words so the pool cannot change a row's shape description). It is **calibrated, not
asserted**: `ops/verify_capstone_parity.py` regenerates all 247 committed ov006
sweep-1 and sweep-2 rows through the fallback and re-verifies them against those
lanes' own pinned fixtures — relocation tables, every `R_ARM_ABS32` image word and
every control diff included.

```
python ops/verify_capstone_parity.py     # 247 rows regenerated; 0 lanes failed
```

246 of the 247 regenerated files are also *textually* identical to the shipped
files; the one difference is the shape-description line of `0x021f50b0`, whose prose
depends on where the decoder gives up inside the literal pool. The byte gate passes
for all 247 either way, which is the claim that matters.

## What the gates had to learn about this population

* **`rsbs rD, rM, #0` is spelled `neg` in Thumb-1, and zero has two spellings.**
  The transcriber's rule keyed on the literal `#0`; the decoder here prints the zero
  immediate of that form as `#0x0`, so the rewrite missed and mwcc rejected
  `rsb r1, r1, #0x0` (`unknown assembler instruction mnemonic`, row `0x02203228`).
  The rule now accepts both spellings of zero — the encoding is the rule, and no
  sweep-1/sweep-2 row contains the mnemonic, so those lanes regenerate byte for
  byte (checked: the parity gate above).
* **A `pc` read is not a `pc` write.** See the two screen corrections above; four
  rows came back from it.
* **One table row does not need the jump-table lane.** The carrier's generator is
  keyed to the sweep-1-era population report; the row is shipped here from
  `transcribe_data_rows.arm_c` directly, with the table extent proved by
  `dispatch_sites` and re-proved by byte identity.

## Source-form rules these rows keep

1. **The body is the measured stream.** Instructions, the literal pool and every
   branch target are read from the image, never guessed.
2. **A data run is emitted as data.** The one row whose extent holds a table uses
   the `dcd` carrier; its entries are measured branch words.
3. **A pool word is a relocation, not a constant.** A word that names something in
   the image is a `native_fn_`/`native_data_` symbol; a magic constant stays numeric.
4. **A duplicated value is counted per pool slot, not per load**, and a genuine
   duplicate gets a distinct alias (`native_data2_`, `native_const_`).
5. **A call is a named symbol, never a raw offset.**
6. **One negative control per row.**
7. **One address-named file per function.**
8. **Lane rules live in `config/rules.d/`, never in the shared array.**
